## Phase 5 — Order Lifecycle (ADR-018)

### What it ships

The complete staff-facing order lifecycle:

- **Branch confirm / reject** — `POST /api/v1/admin/orders/:id/confirm|reject`
- **Kitchen preparing / ready** — `POST /api/v1/admin/orders/:id/preparing|ready`
- **Rider assignment / dispatch / delivered** — `POST /api/v1/riders/deliveries/:id/assign|transition`
- **Cancellation matrix** — 15-min guest self-cancel window on `pending`; staff cancel with mandatory reason; BM/SA-only for late-stage cancels; no cancel on `dispatched`/`completed`
- **Append-only audit** — `order_status_logs` records every transition with actor, reason, note
- **Cross-domain correlation** — every transition mirrored into `domain_events` (ADR-012) as `order.transitioned` with `correlation_id`
- **Branch-scoped RLS** — Slice 2D RLS enabled on `orders`, `order_items`, `order_status_logs`, `deliveries`
- **Kitchen queue read** — `GET /api/v1/staff/kitchen/tickets` for Kitchen Display System

### Why it matters

Before Phase 5, the only staff order operations were ad-hoc SQL updates.
There was no audit trail, no transition validation, no branch scoping.
POS / Kitchen / Rider UIs (Phases 6–9) need a deterministic, auditable,
role-aware state machine to build on — Phase 5 ships that foundation.

### Frozen architecture

`docs/architecture/SPRINT-04-4-ORDER-LIFECYCLE-ARCHITECTURE.md` froze
the canonical transition matrix, cancellation matrix, RLS dependencies,
and API surface as a plan-only artifact. ADR-018 elevates that frozen
architecture to the architecture register as an Accepted v1.0 ADR.

## Phase 3 — Customer Phone / WhatsApp OTP (ADR-016 + ADR-017)

### What it ships

- **7 new auth endpoints** under `/api/v1/auth/`:
  - `POST /auth/otp/request` — issue OTP to phone
  - `POST /auth/otp/verify` — verify OTP and mark phone verified
  - `POST /auth/phone-login` — exchange verified OTP for session tokens
  - `POST /auth/refresh` — rotate refresh token + new access token
  - `POST /auth/logout` — revoke current refresh token
  - `POST /auth/logout-all` — revoke ALL user refresh tokens
  - `GET /auth/sessions` — list active sessions
- **HMAC-SHA256 OTP hashing** with constant-time verification
- **Per-phone + per-IP rate limits** (10/IP/hour for request, 10/IP/min for verify)
- **90-day PII retention** with automatic purge job
- **Refresh token rotation** — each refresh issues a new token and revokes the old
- **Stateless HS256 JWT access tokens** — no DB lookup on every request
- **Customer provisioning flow** — resolve via ADR-005 → create provisional customer → create `auth.users` with placeholder email

### Hard rules

- **D11:** Ordering number `0304-1110495` is **NEVER** used for OTP.
  A dedicated "Telepizza Login" WhatsApp number must be provisioned
  (FU-8, pending operator action).
- **`OTP_HMAC_SECRET`** env var is **REQUIRED** on Render (FU-7,
  pending operator action). Without it, OTP issuance fails closed.

### Migration

`supabase/migrations/20260821000000_adr_016_017_otp.sql` (additive,
~740 lines):

- 4 new tables: `otp_requests`, `otp_attempts`, `customer_phone_verifications`, `auth_refresh_tokens`
- 8 new functions: `expire_stale_otp_requests`, `purge_old_otp_records`, `rotate_previous_pending_otps`, `mark_customer_phone_verified`, `revoke_refresh_token`, `revoke_all_user_refresh_tokens`, `count_otp_requests_by_phone`, `enforce_otp_attempts_append_only`
- 2 new permissions: `otp.manage` (super-admin), `otp.read` (super-admin + customer-support)
- `customers.last_login_at` column added
- Append-only trigger on `otp_attempts` (UPDATE + DELETE blocked)
- Conditional domain event mirror triggers (`customer.otp_verified`, `auth.session_revoked` — ADR-012)
- RLS on all 4 tables
- 6 CHECK constraints enforcing state-machine invariants on `otp_requests`
