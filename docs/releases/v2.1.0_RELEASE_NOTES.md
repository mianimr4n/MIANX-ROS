## What's in this release

### ADR-019 — RBAC Authorization Principal & Permission Model

Formally accepts the as-built authorization surface:

- **5-table permission graph:** `users → user_roles → roles → role_permissions → permissions`, branch-scoped via `user_role_branches`.
- **Dual role namespace** (legacy kebab-case `super-admin` / `branch-manager` / `customer-support` + canonical underscored `platform_super_admin` / `organization_owner` / `branch_manager`) — both resolve to the same permission set via IDENTITY-01 mirror grants.
- **`isSuperAdmin` short-circuit** — `platform_super_admin` and `super-admin` both bypass per-permission lookup (break-glass role).
- **`CUSTOMER_FORBIDDEN_PERMISSIONS` allowlist** — defense-in-depth against customer privilege escalation, alongside the `enforce_customer_role_zero_permissions` trigger.
- **Middleware pipeline:** `createRequireAuth` (JWT) → `createRequireAuthenticatedUser` (DB principal + active status) → `requirePermission(code)` → service-layer branch scoping.
- **Staff assignment constraints:** `ASSIGNABLE_STAFF_ROLES` (7 codes) and `FORBIDDEN_ROLE_CODES` (5 codes) enforced in `backend/api/src/services/staff/assignments.ts`.

### ADR-020 — Canonical Single-Price Menu Catalog & Atomic Price Audit

Formally accepts the Sprint 4 Phase B frozen menu architecture:

- **One price per SKU.** Every `menu_items` row carries exactly one `price` (NOT NULL, `CHECK >= 0`). No more multi-variant pricing indirection.
- **`menu_item_variants` is read-only** (retained for historical `order_items.variant_id` readability). The `trg_prevent_menu_item_variant_writes` trigger hard-blocks any INSERT/UPDATE/DELETE unless `telepizza.allow_variant_writes='on'`.
- **`menu_variant_sku_mappings`** — 1:1 mapping from legacy variant IDs to current SKU IDs (immutable backfill).
- **`update_menu_item_price_atomic` RPC** — single-transaction price update + audit row insert. Idempotent via `(resource_id, action, correlation_id)` unique index. Optimistic concurrency via `p_expected_old_price`.
- **`menu_audit_events`** — append-only audit table with before_data / after_data JSONB snapshots, correlation_id, actor_user_id.
- **`branch_menu_item_overrides` is INACTIVE** — reserved but no runtime code reads it. Per-branch promotions flow through coupons / loyalty rewards (ADR-021).
- **Modifier system** (`modifier_groups`, `modifier_options`, `item_modifier_groups`, `order_item_modifiers`) — orthogonal to the single-price model. Size-scaled price deltas applied at order time.

### ADR-021 — Deals, Coupons & Loyalty Promotion Engine

Formally accepts the three-engine promotions surface:

- **Three independent engines, no shared table:** Coupons + Marketing campaigns & consent + Loyalty program. Each owns its own schema, RPCs, and admin routes.
- **Coupons:** `coupon_validate_discount` read-only validation RPC (quote path); `coupon_redemptions` write on order create (single transaction, `order_id` UNIQUE — one coupon per order).
- **Loyalty ledger (double-entry-shaped):** 5 atomic RPCs (`loyalty_earn_for_order_atomic`, `loyalty_burn_atomic`, `loyalty_adjust_atomic`, `loyalty_expire_atomic`, `loyalty_reverse_atomic`). Each opens `FOR UPDATE` lock, validates balance non-negativity, inserts ledger row, updates balance in a single transaction.
- **3 idempotency indexes:** `loyalty_transactions_earn_order_uidx` (one earn per order), `uq_loyalty_txn_idempotency` (replay is no-op), `uq_loyalty_txn_reverse_once` (one reverse per original).
- **Loyalty reward approval workflow:** `draft → awaiting_approval → approved` (or `rejected`). Only `approved AND is_active` rewards are redeemable.
- **4 loyalty tiers:** member (0 pts, ×1.0), silver (500, ×1.1), gold (2000, ×1.25), platinum (5000, ×1.5).
- **Honest provider states only** for marketing campaigns: `queued | suppressed | submitted | provider_accepted | provider_rejected | failed` — **NO `delivered` status** (WhatsApp/SMS providers cannot reliably report per-message delivery).
- **10 deterministic marketing segments** with documented formula, authoritative_source, time_window, exclusions.
- **Explicit attribution only** — no timing-based inference.

### ADR-022 — Reports & Analytics Framework — Query-Time KPI Registry

Formally accepts the RC4-11 analytics architecture:

- **Query-time computation — no materialized views, no cron.** Verified: zero `MATERIALIZED VIEW` objects in `public` schema; `pg_cron` extension NOT installed.
- **`FORMULA_REGISTRY`** — single authoritative metric contract catalog (`REGISTRY_VERSION = "rc4-2.analytics.v1"`). 6 modules: `sales`, `finance`, `hr`, `inventory`, `purchasing`, `loyalty`.
- **Engine delegates domain math** to domain services (finance → `FinanceService`, HR → `HrPayrollService`, loyalty → `LoyaltyService`) — no formula duplication.
- **Deferred scheduled-report execution:** `analytics_scheduled_reports.execution_status` defaults to `'deferred'`. Honest about the absence of a worker.
- **Exception Center + Data Quality Checks** — manually populated auxiliary tables; no automatic anomaly detection.
- **`ANALYTICS_TIMEZONE = "Asia/Karachi"`** — engine interprets date ranges as Asia/Karachi midnight boundaries; DB stores UTC, conversion at query time.
