## What's in this release

### ADR-027 — Kitchen Ticket Lifecycle & Queue Contract

Formally accepts the as-built kitchen ticket lifecycle:

- **One ticket per order:** `kitchen_tickets.order_id UNIQUE` — there is
  no "multiple tickets per order" pattern. Cancellation, stock reversal,
  and audit all operate on a single row.
- **6-state status machine:** `queued → accepted → preparing → ready →
  completed | cancelled`. `KITCHEN_TICKET_FINAL_STATUSES = {completed,
  cancelled}` — terminal states reject all further transitions with
  `409 TICKET_ALREADY_FINAL`.
- **Allowed transitions matrix:** queued can go to accepted/preparing/
  cancelled; accepted can go to preparing/cancelled; preparing can go
  to ready/cancelled; ready can go to completed/cancelled. Notable:
  `queued → preparing` is legal (kitchen staff can start cooking without
  an explicit accept step).
- **`ORDER_STATUS_MIRROR` mapping:** only `preparing`, `ready`, and
  `cancelled` mirror onto `orders.status` (customer-relevant statuses).
  `accepted` and `completed` stay ticket-local — accepted is kitchen-
  internal, completed is driven by delivery/pickup/bill close.
- **Idempotent transition contract:** `planKitchenTicketTransition()`
  returns `idempotentNoop: true` when `currentStatus === toStatus` —
  the service skips the UPDATE and audit log write. Replaying the same
  transition returns 200 with the existing ticket state (critical for
  the 8s polling UI — double-clicks don't corrupt state).
- **API surface:** `GET /api/v1/kitchen/tickets?branchId=&status=&limit=&offset=`
  (max 100, default 50) + `PATCH /api/v1/kitchen/tickets/:id/status`
  (body: `{status, note?}`). Both require Bearer → `AuthPrincipal` via
  `createRequireAuthenticatedUser`. No `requirePermission` middleware —
  authorization is enforced in the service via `assertKitchenActor` +
  `assertBranchInScope` (defense in depth).
- **Branch isolation (3 layers):**
  1. Database RLS (4 policies on `kitchen_tickets` + `kitchen_ticket_items`,
     gated on `current_user_can_access_kitchen_tickets(branch_id)`).
  2. `current_user_can_access_kitchen_tickets(p_branch_id)` SECURITY
     DEFINER helper — super-admin OR (kitchen/branch-manager role +
     branch match + active + non-customer). Rider/cashier/customer-
     support/customer explicitly denied.
  3. Service-layer `assertKitchenActor(scope)` + `assertBranchInScope(scope, branchId)`.
- **`enforce_kitchen_ticket_branch_match()` trigger:** ensures
  `kitchen_tickets.branch_id == orders.branch_id` on INSERT/UPDATE —
  catches service_role bugs that would otherwise bypass RLS.
- **Polling-not-realtime contract (explicit non-goal):** 8s polling on
  both kitchen UIs. NO Supabase Realtime channels on `kitchen_tickets`
  or `kitchen_ticket_items`. Realtime deferred with trigger condition:
  kitchen device count > 20 per branch OR customer-facing order tracker
  requires sub-second kitchen status updates.

### ADR-028 — Kitchen Order Ticket (KOT) Snapshot & Per-Item Status Model

Formally accepts the as-built KOT data model + atomic stock consume:

- **KOT item snapshots:** `kitchen_ticket_items` table with frozen
  `item_name_snapshot` (text NOT NULL — NOT a FK to `menu_items`),
  `modifiers_snapshot` (JSONB default `'[]'`), `quantity` (int CHECK >0),
  `is_completed` boolean (default false). UNIQUE on
  `(kitchen_ticket_id, order_item_id)` prevents duplicate snapshots.
- **Why snapshot, not FK:** if a cashier edits an `order_items` row
  after the kitchen has started cooking, the kitchen still sees the
  original ticket that was displayed when cooking started. The snapshot
  freezes the kitchen's view; the cashier's edit creates a new audit
  log entry but does NOT retroactively change what the kitchen is cooking.
- **Idempotent Option B creation on order confirm:**
  `createKitchenTicketForConfirmedOrder(supabase, orderId)` in
  `services/kitchen/tickets.ts` — sole entry point for ticket creation.
  Called from `services/orders/management.ts` lines 805-818 when an
  order transitions to `confirmed`. Unique violation (PostgreSQL `23505`)
  is caught as idempotent no-op. NO database trigger — DB-R5 migration
  explicitly chose Option B (same pattern as ADR-024 dine-in bill
  auto-link).
- **Atomic stock consume on `preparing`:** `kitchen_ticket_set_preparing_atomic`
  SECURITY DEFINER RPC (migration `20260730230000`) performs the
  following in a single transaction:
  1. `SELECT FOR UPDATE` on ticket row (prevents concurrent transitions).
  2. Idempotent replay check (returns existing result if already preparing).
  3. Transition guard (`status NOT IN ('queued', 'accepted')` → 409).
  4. Aggregate recipe needs from `order_items × menu_item_inventory_components`.
  5. Stock sufficiency check (raises `Insufficient stock for <item>` on
     shortfall — rolls back the entire transaction).
  6. Insert `stock_movements` rows (movement_type='sale', negative quantity).
  7. UPDATE `inventory_items.current_stock` (decrement).
  8. UPDATE `kitchen_tickets` (status='preparing', started_at=now()).
  9. Mirror onto `orders.status='preparing'` + insert `order_status_logs` row.
- **Cancellation reverses consumed stock:**
  `cancelKitchenTicketForOrder(supabase, orderId, actorUserId)` calls
  `inventory_reverse_kitchen_consumption_atomic` RPC if ticket status
  was `preparing` or `ready`. Inserts positive `stock_movements` rows
  with `movement_type='adjustment'`, `reference_type='kitchen_ticket_reversal'`.
- **Per-item `is_completed` DEFERRED:** column EXISTS on
  `kitchen_ticket_items` (default false), fetched by frontend, but
  always false in Production — no `PATCH /tickets/:id/items/:itemId`
  endpoint exists, no UI affordance to tick individual items complete.
  Trigger: when operators request per-item prep tracking (e.g., for
  multi-course meals where items finish at different times). The column
  pre-positions for V2 — no migration needed when the endpoint is added.
- **KOT print + sequence_number DEFERRED:** `kitchen_tickets.sequence_number`
  integer column EXISTS (nullable) but is NEVER populated by the backend
  (always NULL). No print endpoint, no PDF serializer, no fiscal printer
  integration. Trigger: when a print format is specified AND physical
  printer hardware is in scope (likely ADR-030+ when authored). Same
  pattern as Phase 7 receipts deferral in ADR-023 §8.

### ADR-029 — Kitchen Timers, Priority & Display Contract

Formally accepts the as-built display contract:

- **Client-side elapsed timer:** `ticketTimerStartIso()` fallback chain
  (`startedAt → acceptedAt → createdAt`). `elapsedMinutes(fromIso, now)`
  returns integer minute count. Clock tick: 30s on `AdminKitchen.tsx`,
  15s on `AdminKitchenDashboard.tsx` (acceptable for kitchen display —
  chefs don't need second-precision).
- **Display thresholds (client constants, NOT server-side SLA):**
  - `PREP_WARN_MINUTES = 20` — tickets ≥ 20m elapsed show red.
  - `PREP_TARGET_MINUTES = 15` — tickets 15-19m show yellow.
  - 0-14m shows green.
- **`timerTone(minutes)` returns green/yellow/red.** NO server-side SLA
  tracking, NO `emit_domain_event('kitchen.ticket_late')`, NO audible
  alarm, NO push notifications. The "red" state is purely a visual cue.
  Trigger for SLA tracking: when operators require automated escalation
  to branch-manager on tickets > 20m elapsed.
- **Priority field:** `priority` integer column EXISTS (default 0).
  `priorityBadges(priority, minutesElapsed)` returns `["normal"]` for
  fresh tickets, `["delayed"]` for tickets > 20m, `["high", "delayed"]`
  if both conditions met. `AdminKitchenDashboard.sortTickets` sorts
  `priority DESC, createdAt ASC, sequenceNumber ASC`.
  **However, priority is always 0 in V1** — no mutation endpoint exists,
  no channel-based auto-priority on ticket create. Trigger: when operators
  request manual VIP/urgent escalation.
- **`KITCHEN_STATION_CATALOG` (display-only):** 5 stations hardcoded in
  `lib/admin-kitchen.ts` (pizza/oven/packing/drinks/desserts).
  `KitchenStationsPanel.tsx` renders as collapsed `<details>` with
  `data-testid="kitchen-stations-deferred"`. `KitchenCard.tsx` shows
  "Station · Planned for Phase 2" placeholder pill on every ticket.
  Trigger: when operators request per-station ticket routing (requires
  `kitchen_stations` table + ticket-to-station routing API).
- **KDS navigation modes:** board (all active), queue (queued only),
  ready (ready only), delayed (elapsed ≥ 20m). Two more nav items
  disabled with "Planned for Phase 2" labels: item-view (per-item across
  tickets — deferred until per-item prep ticks), history (completed/
  cancelled archive — deferred until operators request historical KPI
  analysis).
- **8 KPIs on owner ERP, 7 on KDS:** waiting, preparing, ready, delayed,
  average prep time, completed today, kitchen capacity (FOUNDATION —
  unavailable), priority orders (always 0 in V1). Honesty invariant:
  when API request fails or returns empty, KPIs show "—" or "Unavailable"
  rather than `0` (prevents "no orders" misinterpretation when API is down).
- **Insights — rule-based only, NO AI:** `KitchenInsights.tsx` renders
  "Mianx.ai Kitchen Assistant" panel. Despite the name, the panel is
  purely deterministic — no LLM call, no AI prediction, no autonomous
  action. Trigger for AI integration: when operators request predictive
  SLA alerts AND the ADR-013 AI provider boundary is integrated with
  kitchen domain events.
