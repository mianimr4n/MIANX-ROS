## What's New

### ADR-030 — Rider Identity, Dispatch & Assignment Contract

Formally accepts the as-built rider identity + manual dispatch surface:

- **Rider identity:** `rider` role + 1:1 `user_id` UNIQUE + 1:1 `branch_id NOT NULL`. Rider logs in via standard `/staff/login`. No dedicated `/api/v1/rider/*` surface — uses `/api/v1/riders/*` with role-based access differentiation.
- **Manual dispatch:** `POST /api/v1/riders/deliveries/:id/assign` with `delivery.assign` permission (BM/SA only). 8 invariants enforced in order.
- **Idempotent assignment:** same rider + same state = no-op success. Re-assignment to a different rider IS supported (full audit trail).
- **Rider scope:** `isRiderOnly(scope)` helper auto-filters list-assignments to rider's own deliveries.
- **Deferred:** auto-dispatch engine (trigger: branch volume > 50 deliveries/day), rider self-assign queue, rider shift scheduling integration, rider capacity cap, multi-branch riders, rider vehicle + license tracking.

### ADR-031 — Delivery Lifecycle, Pickup & POD Surface

Formally accepts the as-built delivery lifecycle + pickup + POD operational surface:

- **6-state machine:** `pending → assigned → picked-up → delivered | failed | cancelled` with ADR-007 elevation. Append-only `delivery_state_transitions` audit table. SQL trigger + TS validator mirror.
- **Rider transition endpoint:** `POST /api/v1/riders/deliveries/:id/status` accepts only `assigned`/`picked-up`/`delivered`. Riders cannot trigger `failed` or `cancelled` (must escalate to BM/SA).
- **Order mirror:** `picked-up → orders.dispatched`, `delivered → orders.completed` via `mirrorOrderStatus()` with **compensating rollback** pattern.
- **POD-mandatory-for-delivered:** SQL trigger + service-layer pre-check + frontend UI gating (defense in depth). POD row immutable after delivery reaches `delivered`.
- **`picked-up` IS the "out for delivery" state:** ADR-018 §4 explicitly rejected separate `out_for_delivery` status.
- **Deferred:** failed-delivery capture (`delivery_failures` table, trigger: first unresolvable dispute OR >5% failure rate), redelivery flow, customer-facing POD view, live rider map (Realtime + customer RLS), single-transaction delivery+order mirror, delivery SLA tracking.

### ADR-032 — Rider Location, Navigation & Performance Contract

Formally accepts the as-built rider location + navigation + performance surface:

- **Ephemeral GPS storage:** `rider_locations` table with lat/lng/heading/speed/accuracy_m/recorded_at/delivery_id/rider_id. 3 RLS policies (rider self-read, self-insert, branch-staff-read).
- **Storage scope:** pings accepted only when rider has active delivery. Service-layer rejects pings outside active assignment (HTTP 409).
- **24h TTL purge:** `purge_expired_rider_locations(integer)` SECURITY DEFINER function. Idempotent. Only terminal-state deliveries are purged. Job wired in `main.ts`, gated by `TELEPIZZA_RIDER_LOCATION_TTL_JOB=1`.
- **Minimal metadata:** NO reverse-geocoded address, NO device IDs, NO battery level, NO app telemetry, NO IP address.
- **GPS ingest endpoint:** `POST /api/v1/admin/rider-locations` with `delivery.access` permission, rate-limited at 240/min per IP.
- **Partial performance surface:** aggregate KPIs in DeliveryKPIs + DeliveryInsights + DeliveryPerformance. NO per-rider KPIs.
- **Deferred:** per-rider KPI dashboard (trigger: owner request for rider performance reviews OR >20 active riders per branch), `rider_daily_summaries` table, rider mobile app (Phase 12), customer-facing live map (Phase 12), audible alarms + push notifications, TTL job failsafe, reverse geocoding at read-time.
