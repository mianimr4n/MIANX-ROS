## What's in this release

### ADR-023 — POS Cashier Workflow & Order Source Contract

Formally accepts the as-built POS cashier surface:

- **Order source stamp:** every cashier-placed order is stamped with
  `orders.order_source = 'pos'`, distinguishing POS orders from
  `website` and `whatsapp` for reporting and audit.
- **Order type matrix:** `delivery | pickup | dine-in` — each drives a
  distinct server-side flow (dine-in requires `dining_session_id` and
  triggers Option B auto-link to bill; delivery/pickup use order-level
  payments only).
- **Cashier permission contract (segregation of duties):**
  - Cashier HAS `order.create` + `payment.settle` (place orders + settle bills)
  - Cashier LACKS `order.manage` (no transitions), `payment.void` (no voids),
    `payment.override_close` (no emergency closes) — these require
    branch-manager or higher.
- **Branch operational gate:** `assertBranchOperational()` rejects orders
  against closed/inactive branches with `409 BRANCH_NOT_OPERATIONAL`.
- **Cash-only at place-order:** `paymentMethod: z.literal("cash")` enforced
  in request schema. Card / bank / complimentary only available through the
  bill settlement RPC.
- **Idempotency-Key requirement:** every `POST /api/v1/admin/pos/orders`
  requires an `Idempotency-Key` header; retried requests return the original
  order (no duplicates).

### ADR-024 — Dine-in Bill Settlement & Multi-tender Payments

Formally accepts the as-built dine-in bill settlement architecture:

- **`restaurant_bills` lifecycle:** `open → billed → paid|voided`. Paid and
  voided bills are immutable (trigger-enforced). Branch-match trigger ensures
  `restaurant_bills.branch_id = dine_in_sessions.branch_id`.
- **`bill_orders` UNIQUE on `order_id`:** an order belongs to at most one
  bill. Trigger blocks attachment to paid/voided bills.
- **Option B auto-link:** when a dine-in order transitions to `confirmed`
  and has a `dine_in_session_id`, the service attaches it to the session's
  open bill (creating the bill if none exists). Idempotent.
- **`settle_bill_payment_atomic` RPC:** single-transaction settlement with
  `SELECT FOR UPDATE` bill lock. Performs idempotency replay check, branch
  match, bill settleable check, remaining balance computation, method-specific
  validation (cash change computed server-side; complimentary must match
  remaining exactly; card/bank reject overpay), payment INSERT, audit INSERT,
  bill status update.
- **4 payment methods:** `cash`, `card_terminal`, `bank_manual`,
  `complimentary`. No online card gateway integration (documented honestly
  in the `payments` table comment).
- **4 bill split strategies:** `equal` (cent-precise rounding via `splitEqual`
  helper), `by_item`, `by_quantity`, `by_amount` — all with
  `allocation_sum = original_total` CHECK constraint.
- **Deposit → bill application:** `reservation_deposits` can be applied to a
  bill at most once (UNIQUE partial index). Applied amount reduces bill
  remaining balance.
- **RLS hard gate:** `current_user_can_access_restaurant_bills()` helper
  restricts access to cashier + branch-manager + super-admin only.

### ADR-025 — POS Shifts, Z-Report & Cash Reconciliation

Formally accepts the as-built POS shifts + cash reconciliation surface:

- **Two-tier shift model (segregation of duties):**
  - `pos_z_report_events` — append-only shift-close audit (cashier's claim)
  - `cash_reconciliations` — draft → submitted → approved → posted state
    machine (manager's verification + finance's posting)
- **Server-side computation:** `compute_cash_reconciliation_totals` RPC is
  IMMUTABLE + SECURITY DEFINER. Expected cash and variance are computed by
  the database, never the client.
- **Cash reconciliation formula:**
  `expected_cash = opening_float + cash_sales - cash_refunds - cash_drops
  - paid_out_expenses + other_inflows - other_outflows`
  `variance = counted_cash - expected_cash`
- **GL posting on approval:** creates `journal_entries` + `journal_lines`
  (debit `cash_on_hand`, credit `sales_revenue`; `cash_over_short` for
  variance). Idempotent via `finance_postings` UNIQUE on
  `(source_module, source_id)`.
- **Variance handling:** non-zero variance creates a `cash_over_short`
  journal line AND triggers an Exception Center entry (ADR-022) for
  management review.
- **Idempotency + UNIQUE per (branch, business_date, register):**
  `cash_reconciliations` has both an idempotency key UNIQUE index and an
  active-per-day-per-register UNIQUE partial index. Voided recons don't
  block new ones (void-and-redo workflow).
- **Asia/Karachi timezone invariant:** `branches.timezone` NOT NULL with
  default `Asia/Karachi`; `pos_z_report_events.timezone` default
  `Asia/Karachi`. Multi-timezone support deferred to future ADR.
- **`pos_sessions` table deferred:** opening float is captured at cash
  reconciliation time, not at shift open. Sufficient for single-register
  branches; multi-register branches will trigger a future ADR.

### ADR-026 — Branch Sync & Offline-Safe POS Contract

Formally accepts the as-built V1 contract for branch sync and offline safety:

- **"Branch sync" = centralized DB + `branch_id` scoping + RLS.** This is
  NOT a multi-DB synchronization protocol — there's a single centralized
  Supabase Postgres instance. RLS policies enforce that staff can only
  read/write their own branch's rows.
- **"Offline-safe" = Idempotency-Key + optimistic UI.** This is NOT an
  offline-first PWA with local persistence. Server-side invariants make
  retries safe:
  - Idempotency-Key header on all POS POSTs
  - UNIQUE indexes on `(branch_id, idempotency_key)` for orders, payments,
    cash_reconciliations, reservation_deposits
  - Optimistic UI feedback ("Placing order...")
  - Retry returns original response with `idempotentReplay: true`
- **Conflict resolution:**
  - Last-write-wins for non-idempotent writes (status transitions — ADR-018
    §8 idempotent transitions return 200 with current state on retry)
  - Replay for idempotent writes (settlement RPC returns original payment row)
- **RLS hard gate:** `current_user_has_branch_access(branch_id)` on every
  POS table. Even buggy application code cannot leak cross-branch data —
  the database refuses.
- **Network drop handling:** cashier can retry safely (same Idempotency-Key
  returns original response), refresh loses cart (no local persistence —
  known V1 limitation), orders list confirms successful creation.
- **Menu / settings "sync":** handled by ADR-001 (inheritance) + ADR-002
  (versioning). No sync step — branch sees latest global state plus its own
  overrides on every query.
- **Real-time updates deferred:** Supabase Realtime is available but NOT
  used by POS in V1. Cashier UI polls on demand. Will revisit when a branch
  exceeds 200 orders/day.

  python3 scripts/phase_7_verify.py

## Deferred items (with explicit triggers)

Each deferral has an explicit trigger condition documented in the ADRs.
Phase 7 does not claim these as done — they are intentionally V1 boundaries.

| Item | ADR | Trigger to revisit |
|---|---|---|
| Online card gateway (Stripe / Braintree) | ADR-023 §8 | Card payments >30% of revenue |
| Offline PWA with local cart persistence | ADR-026 §5 | Branch reports >5 network drops/week |
| Real-time orders list auto-refresh (Supabase Realtime) | ADR-026 §6 | Branch exceeds 200 orders/day |
| `pos_sessions` table (shift open lifecycle) | ADR-025 §5 | Multi-register branches |
| Receipts format spec + tax invoice + fiscal printer | ADR-023 §8 | Regulatory requirement or printer procurement |
| Multi-timezone support | ADR-025 §9 | International expansion |
| Multi-region DB (read replicas) | ADR-026 §5 | Latency >200ms for any branch |
